## Wissen ändern, ohne versehentlich neue Befugnisse zu erzeugen

Ein Skill kann das Vorgehen nach einer Codeänderung erklären. Ein Tool kann die passende Prüfung tatsächlich ausführen. Die Runtime bestimmt, ob diese Wirkung in der aktuellen Umgebung erreichbar und erlaubt ist. Diese drei Aspekte können unabhängig verändert werden: Eine bessere Testanleitung muss nicht mehr Rechte benötigen; ein neues Lesewerkzeug muss nicht jeden bestehenden Skill verändern.

Erkläre die Trennung am Beispiel einer Release-Anleitung. Die Aussage, für einen Release erst Tests und Build zu prüfen, beschreibt Vorgehenswissen. Sie bedeutet nicht, dass die aktuelle Nutzerfrage eine Veröffentlichung verlangt. Ist eine konkrete Veröffentlichung bereits beauftragt und ihre Ausführung zulässig, darf die Anleitung den Ablauf unterstützen. Eine zusätzliche Freigabeschleife allein wegen des Wortes „Release“ wäre ebenso wenig begründet wie eine ungefragte Veröffentlichung.

Für eigene Systeme muss die Herkunft der Texte klar bleiben. Ein installierter Projekt-Skill, ein vom Nutzer zitierter Buchabschnitt und ein zufällig gefundenes Dokument können ähnliche Sätze enthalten, haben aber nicht dieselbe Stellung im Arbeitsauftrag. Die Anwendung und die tatsächliche Instruktionshierarchie legen diese Stellung fest. Der Loader soll Inhalte nicht durch bloßes Auffinden zu neuen übergeordneten Regeln befördern.

Eine Anweisung kann einen notwendigen technischen Schutz benennen, aber sie setzt ihn nicht allein durch. Umgekehrt sollte Software nicht aus jeder historischen Fehlermeldung eine neue globale Sperre ableiten. Ein früher gesperrter Aufruf dokumentiert die damalige Lage. Maßgeblich für die aktuelle Ausführung sind der gegenwärtige Vertrag, Zustand und Auftrag.

Prüfe beim Entwurf, ob eine fehlende Handlung an Wissen, Fähigkeit oder Befugnis scheitert. Wenn das Tool fehlt, hilft kein umformulierter Skilltext. Wenn die Fähigkeit vorhanden ist, aber der passende Ablauf unbekannt bleibt, kann eine Anleitung helfen. Wenn ein konkreter Zugriff nicht zulässig ist, kann der Agent einen erreichbaren anderen Weg wählen oder das Hindernis benennen. Diese Diagnose vermeidet sowohl unnötige Verweigerung als auch die fälschliche Behauptung neu erworbener Rechte.

## Viele Fähigkeiten über verständliche Auswahl und echte Nachladung erschließen

Bei wenigen Tools kann der vollständige Katalog direkt im Request stehen. Ein größerer Bestand kann einen vorgeschalteten Such- oder Auswahlweg sinnvoll machen. Die KI erhält dann zunächst Beschreibungen und lädt bei Bedarf die konkret benötigte Definition. Die operative Fähigkeit muss anschließend weiterhin durch die Runtime tatsächlich angeboten und ausführbar sein.

Ein Suchtreffer ist dabei nicht automatisch ein aufrufbares Tool. Zeige die Zustandsänderungen: Ein Eintrag wird gefunden, seine vollständige Eingabe- und Ergebnisbeschreibung wird verfügbar, die Runtime bindet beziehungsweise aktiviert den vorgesehenen Handler, und erst dann kann der Modellaufruf ihn nach dem unterstützten Protokoll verwenden. Manche Hosts verbinden diese Schritte; andere verlangen getrennte Aufrufe. Beschreibe den beobachteten Hostvertrag und erfinde keine allgemeine `load_tool`-API.

Die Auswahlbeschreibung sollte die fachliche Domäne und Wirkung erkennbar machen. „Kundenstammdaten nach bestätigter Kundennummer lesen“ unterscheidet sich von „Supportfall anlegen“, obwohl beide im Kundenbereich liegen. Ein sinnvoller Namespace oder Produktname kann gleichnamige Funktionen verschiedener Dienste auseinanderhalten. Technische interne Kennungen dürfen bestehen bleiben, sollten aber nicht die einzige Information für die semantische Auswahl sein.

Für eine Umsetzung ist entscheidend, dass Beschreibung und erreichbare Version zusammenpassen. Ein deaktiviertes oder nicht verfügbares Tool sollte nicht als frei nutzbare Fähigkeit beworben werden. Ändert sich die Verfügbarkeit zwischen Auswahl und Aufruf, muss das Ergebnis den tatsächlichen Zustand erklären. Der Agent kann dann eine passende Alternative wählen, statt denselben nicht vorhandenen Namen immer wieder anzufordern.

Prüfe bei einer Suchlösung sowohl Recall für tatsächlich benötigte Fähigkeiten als auch unnötige Treffer. Eine größere Trefferliste ist nicht automatisch besser. Die Modellfälle sollten unterschiedliche Nutzerformulierungen und relevante Verwechslungen enthalten; die Runtimeprüfungen sollten belegen, dass ein gefundener Name auf den richtigen Handler zeigt. Dynamisches Finden ist eine Möglichkeit, den Handlungsraum nutzbar zu halten, kein Muss für eine Anwendung mit fünf klar beschriebenen Werkzeugen.
