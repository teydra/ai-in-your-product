## Browseranfrage in einen Providerrequest übersetzen

Verfolge zuerst die eigene Browsernachricht. Im Begleitprogramm enthält sie `chat_id` und `text`. `chat_id` verweist auf einen Datensatz in der laufenden Anwendung. Das Backend sucht diesen Gesprächsverlauf heraus und prüft die Eingabe. `build_request` erzeugt danach eine tiefe Kopie der gespeicherten Nachrichten und ergänzt die neue User-Nachricht. Die Kopie ist wichtig: Solange der Provideraufruf noch scheitern kann, bleibt der bisher erfolgreich gespeicherte Modellverlauf unverändert. Ein wiederholter Versuch soll dieselbe Nachricht nicht allein durch einen vorher fehlgeschlagenen Request mehrfach enthalten.

Erst jetzt entsteht der Providerrequest mit Modellkennung, Ausgabelimit, übergeordneten Instruktionen und Nachrichten. Im konkreten Anthropic-Vertrag heißen diese Felder `model`, `max_tokens`, `system` und `messages`. Die lokale `chat_id` wird hier nicht an den Anbieter weitergereicht. Auch eine eigene UI-Einstellung wird nur dann modellwirksam, wenn das Backend sie bewusst in eine unterstützte Instruktion oder API-Option übersetzt. Ein neuer Browserparameter erzeugt keine entsprechende Fähigkeit beim Dienst.

Zeige bei Bedarf zusätzlich die Transporthülle: Der Provideradapter sendet den JSON-Körper per HTTP POST an den Messages-Endpunkt und setzt Inhaltstyp, API-Version und Authentisierung in den Headern. JSON-Felder, HTTP-Header und Prozessumgebung erfüllen verschiedene Aufgaben. Ein API-Schlüssel aus der Umgebung wird im Backend gelesen; daraus folgt nicht, dass er im Textkontext oder in der sichtbaren technischen Ansicht stehen muss. Gib in einer Diagnose den gebauten, bereinigten Anfragekörper und die relevante Fehlermeldung wieder, ohne geheime Header zu kopieren.

Verwende für Nachverfolgung eindeutige Namen. Eine eigene `chat_id` identifiziert das Gespräch. Ein künftig eingeführter `turn_id` könnte einen einzelnen Sendevorgang identifizieren. Eine vom Provider zurückgelieferte Nachrichtenkennung bezeichnet dessen Antwort; ein HTTP-Request-Identifier kann wiederum ein anderes Supportmerkmal sein. Lege diese Angaben als getrennte Felder ab und erfinde keine Providerkennung aus einer eigenen laufenden Nummer. Wenn eine Nummer in einer Erklärung nur illustriert ist, kennzeichne sie als Beispielwert. Der entscheidende Nachweis bleibt der tatsächlich gesendete Request, nicht eine plausible Erzählung über seinen mutmaßlichen Inhalt.

## Antwortdarstellung und Verlaufsspeicherung trennen

Behandle eine Providerantwort zunächst als strukturiertes Datenobjekt. Im Beispiel enthält `content` eine geordnete Liste typisierter Blöcke. Für die Chatdarstellung werden die unterstützten Textblöcke ausgelesen. Für die nächste Provideranfrage können zusätzlich unterstützte Thinking-Blöcke oder andere vom konkreten Vertrag benötigte Inhalte erhalten bleiben. Diese beiden Zwecke verlangen nicht dieselbe Darstellung. Ein auf dem Bildschirm ausgeblendeter Block ist nicht zwangsläufig überflüssig für die Fortsetzung; eine Verbrauchszahl gehört umgekehrt nicht allein deshalb in die Nachrichtenliste, weil sie im Antwortobjekt steht.

Das kleine Programm akzeptiert bewusst nur die von seinem Parser behandelten Blocktypen und Abschlusszustände. Wenn ein neuer Zustand hinzukommt, prüfe die dafür nötige Semantik. Ein `tool_use`-Block ist beispielsweise keine alternative Schreibweise einer fertigen Textantwort. Ein automatisches Umwandeln unbekannter Strukturen in einen String würde das Problem verdecken. Erweiterungen müssen festlegen, wie der Inhalt angezeigt, gespeichert und gegebenenfalls fortgesetzt wird. Für eine reine Textanwendung ist ein verständlicher Fehler bei einer unerwarteten Rückgabe oft die richtige anfängliche Behandlung.

Speichere einen erfolgreich auswertbaren Zug zusammenhängend: die gerade gesendete User-Nachricht und die zulässigen Inhaltsblöcke der Assistant-Antwort. Der bestehende Code hängt beide erst nach der Antwortprüfung an den Verlauf. Technische Hinweise bleiben getrennt. „Dienst überlastet“ stammt aus der Anwendung, wenn der Anbieter keine nutzbare Modellantwort geliefert hat. Wird dieser Hinweis als Assistant-Nachricht gespeichert, könnte der nächste Modellaufruf ihn fälschlich als vorangegangene Aussage des Modells interpretieren. Ein späteres Produkt kann fehlgeschlagene Sendeversuche durchaus als eigene UI-Ereignisse dauerhaft aufbewahren, ohne sie dem Modell als erfolgreiche Unterhaltung zu übergeben.

Erkläre die sichtbare Ausgabe an ihrer tatsächlichen Einfügung. `textContent` zeigt den Code im Browser als Text. Es führt die Funktion weder aus noch legt es eine Projektdatei an. Soll später Markdown formatiert werden, braucht der Renderer einen passenden Umgang mit Links und HTML; die bloße Rückgabe aus einer Modell-API macht Inhalt nicht vertrauenswürdig. Soll Code ausführbar werden, ist das eine gesonderte Produktfähigkeit mit einem eigenen Ausführungsweg. Die Darstellung bleibt bis dahin eine Darstellung, auch wenn der gezeigte Code syntaktisch vollständig aussieht.
