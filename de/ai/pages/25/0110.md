## Werkzeuge in der Sprache ihrer tatsächlichen Wirkung entwerfen

Neue Werkzeuge können neue Systeme erreichbar machen oder eine vorhandene Wirkung präziser anbieten. Ein allgemeiner Prozesszugriff, ein Lesewerkzeug und ein fachlicher Aufruf wie `create_ticket` unterscheiden sich darin, welche Entscheidungen das Modell noch treffen muss und welche die Anwendung bereits verlässlich übernimmt. Wähle die Granularität nach der Aufgabe und dem kontrollierbaren Wirkungsbereich.

Ein guter Name beschreibt den fachlichen Gegenstand und die Operation. Ein Kundenwerkzeug kann etwa einen bestimmten Kundendatensatz lesen; ein Aufgabentool einen Entwurf anlegen; ein Sensorwerkzeug die aktuelle Beobachtung einer Zone liefern. Die Description ergänzt Anlass, benötigte Eingabe, Ergebnis und relevante Grenzen. Ein Name wie `smart_action` verbirgt diese Unterschiede. Eine reine Backend-Funktionsbezeichnung kann genauso wenig helfen, wenn ihre Bedeutung aus dem verfügbaren Kontext nicht erkennbar ist.

Gehe bei einer Erklärung vom vorhandenen Toolkatalog aus. Welche Fähigkeit wird dadurch tatsächlich erreichbar, und welche nur leichter aufrufbar? Der Name `control_irrigation_zone` in einer Beispielsammlung ist noch keine angeschlossene Anlage. Eine Runtime müsste Gerätezuordnung, verfügbare Aktionen und Rückmeldungen erst implementieren. Ein geeignetes Modell kann beschriebene Funktionen im Kontext verwenden; daraus folgt nicht, dass jede neue Funktion ohne Prüfung zuverlässig ausgewählt und ausgeführt wird.

Für ein eigenes Produkt ist ein Werkzeugvertrag nützlich, der Rückgaben an vorherige Eingaben anschließbar macht. Ein Suchtreffer liefert beispielsweise eine Kennung, die das Lesewerkzeug akzeptiert. Eine Vorschau kann eine konkrete Version nennen, gegen die später übernommen wird. Die KI kann die Fähigkeiten dann sinnvoll kombinieren, ohne unsichere Vermutungen über unbekannte Kennungen anzustellen.

Prüfe sowohl Auswahlqualität als auch reale Wirkung. Gute Descriptions helfen bei der ersten; Handler, Zustandsprüfung und kontrollierte Ausführung sichern die zweite. Ein Modell kann das richtige Tool wählen und dennoch wegen fehlender Daten scheitern. Ein Handler kann technisch korrekt arbeiten und durch eine missverständliche Description ständig falsch verwendet werden. Diese Fehlerursachen benötigen unterschiedliche Verbesserungen.

## Fehlendes Vorgehenswissen von fehlendem Zugriff unterscheiden

Ein Terminalwerkzeug kann Programme starten, erklärt aber nicht automatisch den richtigen Testbefehl dieses Projekts. Umgekehrt kann eine Anleitung den Testbefehl nennen, ohne ihn ausführen zu können. Diese Trennung lässt sich im Preisfall unmittelbar zeigen: `run_command` stellt den erlaubten Prozessweg bereit; `price-changes` erklärt die fachliche Rundung und den passenden Prüfschritt.

Wenn ein Agent scheitert, bestimme die konkrete Lücke. Ist die relevante Datei nicht zugänglich? Fehlt die Anleitung? Ist die Anleitung geladen, aber falsch angewendet? Verwendet der Handler eine andere Umgebung als beschrieben? Im absichtlich fehlerhaften ersten Schreibversuch fehlt kein Skilltext mehr. Dort ist die Umsetzung einer bereits verfügbaren Regel unzureichend. Mehr Wissensabruf wäre dafür nicht automatisch die richtige Reparatur.

Arbeitswissen kann auch an einer anderen Stelle liegen: kurze Regeln dauerhaft in den Anweisungen, eine passende Referenzdatei, ein freigegebenes Playbook oder ein dokumentierter Toolvertrag. Für wenige kurze, regelmäßig notwendige Angaben kann direkte Bereitstellung einfacher sein als ein zusätzlicher Such- und Ladeweg. Für umfangreiche spezialisierte Anleitungen kann gezieltes Laden den nächsten Modellaufruf übersichtlicher machen.

Beim Bauen beschreibe zunächst, welche Entscheidung ohne dieses Wissen falsch getroffen werden könnte. Daraus ergeben sich Anlass und Inhalt des Skills. Eine Seite voller allgemein richtiger Agentenregeln hilft wenig, wenn sie die aktuelle Frage nach Rundung oder Testumgebung nicht beantwortet. Ebenso wenig sollte eine Anleitung jede bedeutungsabhängige Wahl durch eine starre Schrittfolge ersetzen.

Eine hilfreiche Erklärung benennt schließlich, was nach dem Laden anders ist: Die Modellgewichte und die Dateirechte bleiben dadurch nicht magisch erweitert; der aktuelle Kontext enthält zusätzliche nutzbare Information. Erst wenn die KI diese Information in eine geeignete Aktion oder Erklärung überführt, entsteht ihr praktischer Nutzen. Die tatsächliche Wirkung dieses Vorgehens muss an passenden Fällen geprüft werden.
