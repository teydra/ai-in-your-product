# KI-Seite 99 · Kapitel 5 — Offen, ohne dass alles offensteht

Wissen für deinen Assistenten zu Seite 99 der Ausgabe 25. Der Buchtext steht gesondert auf der [Menschenseite 99](../../../human/pages/25/0099.md). Abschnitte: `ch05/c01-datei-suchen`, `ch05/c02-preiscode-lesen`, `ch05/c03-tests-lesen`.

## Schritt 1: Aus dem Auftrag eine überprüfbare Dateisuche machen

Die erste vorgegebene Modellantwort enthält eine kurze Assistant-Meldung und den Aufruf `c01`. Seine Funktion heißt `search_files`; seine Argumentzeichenkette enthält `{"query":"prices"}`. Das Modell formuliert damit eine Suchanfrage. Die Runtime durchsucht die Dateinamen im ausgewählten Projekt. Die beiden Tätigkeiten haben unterschiedliche Akteure, obwohl die Oberfläche sie gemeinsam als Arbeit des Agenten zeigen kann.

Das Ergebnis nennt `src/prices.py` und `tests/test_prices.py`. Die Kenntnis dieser Pfade rechtfertigt die nächste gezielte Lesung. Sie verrät noch nicht, ob die erste Datei eine Preisfunktion enthält, welche Rundungsart sie nutzt oder welche Ergebnisse der Test verlangt. Die Rückgabe wird mit `call_id: "c01"` als `function_call_output` in den Verlauf aufgenommen.

Nach diesem Schritt hat der Verlauf fünf Einträge: Nutzertext, Skill-Katalog, erste Assistant-Meldung, Suchaufruf und Suchergebnis. Genau diesen Stand enthält Request-Vorlage 2. Der Preiscode erscheint erst später. Wer beim Erklären bereits aus der späteren Datei zitiert, muss diesen Vorgriff benennen; er darf ihn nicht als schon verfügbares Modellwissen behandeln.

Für einen realen Agenten ist `prices` ein aus dem Auftrag abgeleiteter Suchversuch. Ergibt er keine Treffer, liefert das Suchverfahren selbst einen Ansatzpunkt: Es sucht hier Namen, nicht Inhalte. Eine andere passende Fähigkeit könnte Programmtext nach einer Preisfunktion durchsuchen. Gibt es viele Treffer, können Pfadkontext oder eine begrenzte Lesung helfen. Das Ziel ist die relevante Implementierung, nicht das ritualisierte Ausführen genau dieses Suchstrings.

Eine Runtime sollte ihr Suchergebnis so beschreiben, dass leerer Trefferbestand und fehlgeschlagene Suche erkennbar verschieden sind. Eine leere gültige Liste ist neue Information über den durchsuchten Raum. Ein Fehler wegen fehlendem Zugriff ist kein Beleg, dass die Datei nicht existiert. Beides verlangt einen anderen nächsten Schritt als eine erfolgreiche Suche mit den beiden im Buch genannten Pfaden.

## Schritt 2: Den gefundenen Pfad in tatsächlichen Programmtext überführen

Aufruf `c02` verwendet `read_file` mit `path: "src/prices.py"`. Der Pfad stammt aus der vorangegangenen Suche. Die Runtime löst ihn innerhalb des ausgewählten Projekts auf und liest die Datei. Im Responses-Rückgabe-Item steht der vollständige Text in `output`. Das eigene Replayprotokoll bewahrt zusätzlich ein Objekt mit Pfad und Inhalt; diese Begleitform ist nicht das unverändert verwendete Provider-Item.

Nun kann die KI die konkrete Funktion analysieren: Aus den Eingaben werden `Decimal`-Werte, diese werden ausgehend von `Decimal("0")` addiert und schließlich mit `str(amount)` zurückgegeben. Für das Erklärziel ist die fehlende ausdrückliche Festlegung auf Hundertstel relevant. Vermeide zugleich die voreilige Aussage, eine beliebige Formatzeile sei schon die richtige gesamte Lösung. Die genaue vereinbarte Rundung und die vorhandenen Tests gehören ebenfalls zum Fall.

Nach der Lesung enthält die dritte Request-Vorlage sieben Items. Es ist noch keine Datei geändert. Auch ein Modell, das im Text bereits die richtige Korrektur beschreiben könnte, müsste sie über eine tatsächlich angebundene Schreibfähigkeit ausführen lassen. Diese Trennung ist an der Seite besonders wichtig, weil sichtbarer Quellcode leicht wie bereits bearbeiteter Code wirkt.

Bei einer eigenen Anwendung sollte die Rückgabe klar machen, ob ein vollständiger Text oder nur ein Ausschnitt geliefert wurde. Ein begrenztes Tool kann weiterhin nützlich sein, wenn Umfang und Lesemöglichkeit für den Rest bekannt sind. Eine Änderung auf Grundlage einer älteren Beobachtung muss außerdem mit dem inzwischen vorhandenen Zustand vereinbar bleiben.

Lass eine Erklärung vom beobachteten Ausdruck ausgehen: `return str(amount)` steht wirklich in dieser Datei. Daraus folgt eine überprüfbare Hypothese über die Ausgabe. Bei anderem Code kann der notwendige Eingriff anders liegen, etwa bereits in einer vorgeschalteten Berechnung. Ein Agent sollte deshalb die tatsächliche Ursache bestimmen, statt den Dateinamen oder den Buchsatz als universelles Rezept für Preisfehler zu behandeln.

## Schritt 3: Vorhandene Erwartungen lesen, ohne einen Testlauf zu behaupten

Aufruf `c03` liest `tests/test_prices.py`. Die Rückgabe ist Programmtext. Sie beschreibt drei Erwartungen: `4.10 + 6.20` ergibt `10.30`, `12.345` ergibt `12.35`, die leere Liste ergibt `0.00`. Diese Werte sind bereits im Projekt festgelegt. Sie werden nicht von der KI nachträglich aus einer gewünschten Erfolgsantwort erfunden.

Der Test importiert `total` aus der Quelldatei, durchläuft die Fälle und vergleicht den tatsächlichen Rückgabetext mit dem erwarteten Text. Beim ersten Unterschied schreibt er eine Fehlermeldung nach `stderr` und beendet den Prozess mit Code `1`. Erst wenn alle Fälle ohne diesen Abbruch durchlaufen wurden, erscheint `PASS: 3 price cases`. Diese Programmstruktur erklärt später, was aus den beiden Testausgaben wirklich geschlossen werden kann.

Jetzt sind die Tests nur gelesen. Die vierte Request-Vorlage enthält neun Items und damit ihre Anforderungen, aber kein ausgeführtes Testergebnis. Sage deshalb weder, die Ausgangsversion habe „drei rote Tests“, noch, die gelesenen Fälle seien schon bestätigt. Welche Fälle beim ersten tatsächlichen Testlauf erreicht werden, ergibt sich aus dessen Ausführung.

Für eine Zusammenarbeit an echtem Code sind vorhandene Tests wichtige Evidenz, aber nicht automatisch die vollständige fachliche Wahrheit. Stimmen Test, dokumentierte Anforderung und aktueller Nutzerauftrag überein, ergibt sich ein klarer lokaler Vertrag. Bei einem Widerspruch muss der Agent diesen benennen und die maßgebliche Anforderung klären. Das ist etwas anderes, als eine unbequeme Erwartung passend zum eigenen Code umzuschreiben.

Der Nutzerauftrag und diese drei Fälle reichen für den kleinen Buchabschnitt. Zusätzliche Fälle sind dann sinnvoll, wenn sie ein konkretes verbleibendes Risiko beantworten, etwa eine ausdrücklich gewünschte Behandlung negativer Werte. Bloß zusätzliche Testmenge erzeugt noch keine bessere Prüfung. Für die nächste Seite ist entscheidend: Die KI besitzt jetzt überprüfbare Sollwerte und kann ihre vorgeschlagene Implementierung daran messen.
