## JSON und den passenden API-Vertrag erklären

Beginne eine API-Erklärung bei Sender und Empfänger. Die Anwendung möchte einem Dienst Eingaben übermitteln und dessen Rückgabe verarbeiten. Der Vertrag legt fest, welche Felder, Typen und Abläufe dafür gelten. JSON ist eine mögliche Darstellung dieser Daten. Ein Objekt verbindet Feldnamen mit Werten; eine Liste enthält geordnete Elemente. Eine Zeichenfolge mit der Aufschrift „role: system“ ist zunächst Text. Welche Bedeutung sie erhält, hängt davon ab, an welcher strukturellen Stelle das Programm sie tatsächlich übergibt.

Ordne jedes gezeigte JSON-Dokument seiner Verbindung zu. Leihregals Browser sendet etwa `{"begriff": "Phantomspeisung", "geraet": "M2"}` an den eigenen Server. Dieses Format hat die Anwendung selbst gewählt. Das Backend kann daraus eine Anbieteranfrage bauen, die andere Felder enthält. Es kann außerdem einen Betriebsdatensatz für Laufzeit und Fehler speichern. Keines dieser drei Dokumente wird allein durch ähnliche Feldnamen identisch mit den anderen. Eine nützliche Erklärung nennt bei jedem Dokument seinen Erzeuger, Empfänger und Zweck.

Halte die im Buch verglichenen Schnittstellen getrennt: Anthropic Messages nutzt im Beispiel `system` und `messages`, OpenAI Responses `instructions` und `input`, Gemini `generateContent` `systemInstruction` sowie `contents` mit `parts`. Die konkrete Modelladressierung und die Ausgabelimits gehören zum jeweils gewählten Vertrag. Übertrage nicht nur die Feldnamen eines Beispiels in das SDK eines anderen Anbieters. Ein SDK kann zudem eigene Hilfsobjekte anbieten, die beim HTTP-Transport anders serialisiert werden.

Für eine beauftragte Umsetzung lege zunächst einen passenden Provideradapter fest. Seine Aufgabe ist, ein fachlich benanntes internes Eingabeobjekt in den unterstützten Anbieterrequest zu übersetzen und Rückgaben wieder einzuordnen. Halte diese Übersetzung klein genug, dass man eine Anfrage samt zugehöriger Antwort tatsächlich lesen kann. So bleibt ein Anbieterwechsel eine bewusste Anpassung des Vertrags. Ein riesiges gemeinsames Objekt, dessen unbekannte Felder überall still ignoriert werden, macht Fehler schwer erkennbar.

Das Referenzbeispiel ist an [Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create) ausgerichtet. Bei einer aktuellen Implementierung sind Endpunkt, SDK-Version und Modellunterstützung gemeinsam zu prüfen.

## Eine API-Erklärung beim sichtbaren Ergebnis beginnen

Das Buch öffnet keinen Brief, bevor das Ergebnis sichtbar ist: ein Feld „Begriff erklären“ unter der Gerätebeschreibung des Kondensatormikrofons M2, eine Frage, eine Antwort. Übernimm diese Reihenfolge, wenn du jemandem einen Modellaufruf erklärst. Beginne bei dem, was die Person in ihrem Produkt sieht oder sehen will: einer Antwortblase, einem Vorschlag, einem Button, einer Fehlermeldung. Gehe danach zu den Briefen, die dieses Ergebnis erzeugen.

So hat jedes Feld sofort einen Ort. `content[0].text` ist dann nicht irgendein Pfad, sondern der Text in der Antwortblase. `stop_reason` entscheidet, ob ein Hinweis auf eine abgeschnittene Antwort erscheint. `system` ist der Auftrag, den der Helfer nie sieht. Wer zuerst die Felder lernt und erst danach erfährt, wofür sie gut sind, behält eine Liste. Wer vom Ergebnis ausgeht, behält einen Ablauf.

Bei einer Umsetzung gilt dieselbe Richtung. Kläre, welche sichtbare Wirkung entstehen soll, bevor du Felder, Schemas oder Endpunkte auswählst. Ein Feld, das in der Oberfläche oder in einer Entscheidung keine Wirkung hat, braucht eine Begründung, sonst ist es Ballast.
