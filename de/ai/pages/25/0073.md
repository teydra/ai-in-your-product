## Aufruf, Argumenttext und Kennungen sauber auseinanderhalten

Lies den Werkzeugaufruf von außen nach innen. `type: "function_call"` bezeichnet das Ausgabe-Item. `name: "run_command"` verweist auf das angebotene Werkzeug. `call_id: "call_01"` ordnet diesem einzelnen Aufruf später seine Rückgabe zu. `arguments` ist im gezeigten Responses-Item eine Zeichenkette, deren Inhalt wiederum JSON ist. Die Runtime dekodiert diesen Inhalt zu `{"command":"rg --files"}` und kann danach den Wert von `command` verwenden.

Die entkommenen Anführungszeichen sind eine Eigenschaft der äußeren Darstellung. Es werden weder Backslashes an ein Terminal getippt noch muss das Modell ein zweites Programm zur „JSON-Entschlüsselung“ aufrufen. Zeige bei Unsicherheit genau zwei Ansichten: das Originalfeld als String und das einmal geparste Argumentobjekt. Erkläre, welcher Parser welche Schicht liest. Vermeide manuell zusammengeklebte JSON-Strings in Implementationen; ein Serializer erzeugt die nötige Maskierung aus dem wirklichen Objekt.

Für den Rückweg verwendet die Anwendung dieselbe vom Aufruf gelieferte `call_id`. Der neue Modellrequest darf das Ergebnis nicht anhand des Werkzeugnamens allein zuordnen: Zwei Aufrufe von `read_file` können verschiedene Dateien betreffen. Eine Antwortkennung wie `resp_01` hat eine andere Aufgabe. Sie bezeichnet einen Gesprächsanschluss und ersetzt die Aufrufkennung nicht. Die kurzen Kennungen des Buchs sind Lehrwerte. In einer realen Integration sind die tatsächlichen Providerwerte beziehungsweise der dokumentierte eigene Zustandsweg zu verwenden.

Halte zusätzliche Anwendungskennungen außerhalb des Providerbodys, solange dessen Vertrag sie nicht vorsieht. Nutzerkonto, ausgewählter Projektordner und interne Laufnummer können serverseitig zum Aufruf gespeichert werden. Sie müssen nicht als erfundene Felder `user_id`, `project_id` oder `approved` im gezeigten API-JSON erscheinen. Falls das Modell eine Objektkennung benötigt, liefere sie über den konkret vorgesehenen Kontext oder Werkzeugvertrag; ihre Existenz beweist weiterhin kein Zugriffsrecht.

Eine nützliche Adapterprüfung verbindet zwei gleichnamige Aufrufe mit zwei unterschiedlichen Rückgaben. Sie muss nachweisen, dass jede Rückgabe beim richtigen offenen Aufruf landet. Parserfehler und eine unbekannte Aufrufkennung verlangen eine klare Fehlerbehandlung, nicht die willkürliche Auswahl des letzten Tools.

## Vom Befehlstext zum wirklichen Prozess führen

Ein Terminal ist eine Oberfläche zum Eingeben und Anzeigen von Text. Eine Shell interpretiert eine Befehlssprache. Ein Programm ist der tatsächlich gestartete Prozess. Diese drei Begriffe werden häufig zu „der Agent benutzt das Terminal“ zusammengezogen. Im Buchbeispiel ist kein sichtbares Fenster erforderlich: Die Runtime startet `rg` direkt mit dem Argument `--files` und einem zuvor bestimmten Arbeitsverzeichnis.

Der Nutzer hat das Projekt in der Anwendung ausgewählt. Die Anwendung bindet den Toolhandler an diesen Ordner. Das Modell muss deshalb keinen absoluten Pfad des Rechners erfinden. `src/prices.py` ist ein relativer Dateipfad innerhalb dieser Bindung. Ein anderer aktueller Arbeitsordner würde denselben Text auf einen anderen Ort beziehen. Erkläre diese Zuordnung ausdrücklich, wenn jemand fragt, woher der Agent „weiß, auf welchem Computer“ er arbeitet.

Für einen festen Aufruf kann ein Handler einen geprüften Befehlswert auf einen Argumentvektor abbilden. Genau das tut der Kapitel-4-Replay für `rg --files`. Wird dagegen eine Shell gebraucht, entsteht ein anderer Ausführungsvertrag: Sonderzeichen, Umleitungen und Unterprozesse haben dann Bedeutung. Ein Schema mit einem Stringfeld löst diese Fragen nicht. Ein eigenes Produkt sollte die benötigte Wirkung gezielt anbieten; ein allgemeines Shellwerkzeug verlangt eine entsprechend durchgesetzte Ausführungsumgebung.

Laufumgebung, Zeitlimit und Prozessausgabe sind Teil der Fähigkeit. Fehlt `rg`, ist das eine fehlende Programmabhängigkeit, keine unzureichende Formulierung des Nutzerwunschs. Bei einem echten Fehler muss die Runtime Diagnose und tatsächlichen Status zurückgeben. Das Modell kann dann einen verfügbaren Ersatzweg wählen, etwa ein anderes Suchwerkzeug, sofern dessen Vertrag passt. Wiederholt denselben nicht installierten Befehl zu senden bringt keine neue Information.

Zeige zum Schluss die konkrete Wirkung des Aufrufs: Dateipfade wurden ermittelt, aber keine Datei geändert. Auch der erfolgreiche Start eines Testprogramms wäre noch vom Ergebnis dieses Tests zu unterscheiden. Diese Unterschiede bleiben bei Browser- und Datenbankwerkzeugen bestehen, obwohl dort keine Shell beteiligt sein muss.

## Die Runtime als Verbindung zwischen Entscheidung und Wirkung bauen

Der strukturierte Modelloutput ist eine Anforderung. Die Runtime erkennt den Ausgabetyp, löst den Werkzeugnamen auf, liest die Argumente und entscheidet nach dem aktuellen Ausführungsvertrag über die tatsächliche Aktion. Zeige diese Übergabe an `run_command`, bevor du über abstrakte „Kontrolle“ sprichst. Erst wenn der Prozess gestartet wird, entsteht eine reale Handlung.

Die drei Buchfälle sind Ausführung, Ablehnung und Warten auf eine fehlende Freigabe. Sie dürfen nicht auf denselben grünen Erfolgsstatus reduziert werden. Bei einer Ablehnung wird das Werkzeug nicht gestartet; das Modell erhält den konkreten Grund. Bei einem wartenden Aufruf muss die Anwendung wissen, wer welche konkrete Wirkung entscheiden kann und wie der Lauf danach fortgesetzt wird. Eine erneute Frage an das Modell ersetzt diese Nutzerentscheidung nicht. Bestehende gültige Befugnisse werden durch ein Freigabefeld im Modelloutput weder geschaffen noch aufgehoben.

Implementiere Grenzen dort, wo sie wirken. Der Handler kann auf einen Projektordner und bestimmte Operationen beschränkt sein. Für einen Prozess, der weitere Programme starten kann, muss die erlaubte Umgebung auch diese erreichbaren Wirkungen abdecken. Eine Liste verbotener Wörter im Befehlstext genügt dafür nicht. Der isolierte Preis-Replay zeigt einen eng begrenzten Lehrvertrag, keine vollständige Sandbox für beliebigen fremden Code.

Die Runtime braucht außerdem eine belastbare Fehlergrenze. Ein unbekanntes Tool, ungültige Argumente, fehlender Zugriff und ein Fehler nach Prozessstart sind unterschiedliche Ergebnisse. Gib dem Modell genug Information, um einen passenden nächsten Schritt zu wählen. Eine nicht ausgeführte Aktion kann nach Korrektur erneut angefordert werden. Bei einer gestarteten Schreibaktion mit unbekanntem Ausgang ist zunächst die Wirkung zu klären; eine blinde Wiederholung kann doppelt schreiben.

Bei mehreren Anforderungen richtet sich Parallelität nach Abhängigkeiten und gemeinsamem Zustand. Zwei unabhängige Lesungen können nebeneinander stattfinden. Schreiben und anschließendes Testen derselben Datei bilden im Preisfall eine Abhängigkeit. Die Software darf diese Beziehung sichern, ohne den gesamten inhaltlichen Lösungsweg vorab festzulegen. So bleiben semantische Entscheidungen bei der KI und zuverlässige Ausführungsgarantien in der Runtime.
